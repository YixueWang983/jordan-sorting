\section{Methodological Positioning}
\label{sec:method-positioning}

Experimental algorithmics complements abstract analysis by studying concrete
algorithms, implementations, inputs, and machines under an explicit design
\parencite{mcgeoch2012guide}. In the related algorithm-engineering perspective,
design, analysis, implementation, and experimental evaluation form a feedback
cycle rather than interchangeable sources of evidence
\parencite{sanders2009engineering}. This thesis uses that separation to keep
the historical theorem, the ordinary-list implementation, and the measured
execution scopes distinct.

Performance measurements also require explicit treatment of uncertainty and
experimental setup. \Textcite{kalibera2013benchmarking} motivate repetition
and reporting of variation, while \textcite{mytkowicz2009wrong} demonstrate
that apparently innocuous setup choices can bias performance conclusions. The
pre-specified protocol therefore retains repeated raw measurements, rotates algorithm
positions, records the runtime environment, and limits inference to the tested
cases and machine. These references motivate the design; the study does not
claim to implement every hierarchical statistical procedure proposed in that
literature.

\section{Pilot and Formal Experiments}
\label{sec:method-experiment-stages}

The evaluation was conducted in two stages: a pilot experiment used to verify
the protocol and a subsequent formal experiment used as the thesis-facing
quantitative evidence. Their archived repository identifiers are retained only
for provenance. The pilot is used in this thesis solely for the directional
replication analysis; all primary quantitative results come from the formal
experiment.

\section{Study Scope}
\label{sec:method-scope}

% Claims: M-01, M-02, M-09; limitations L-02, L-05, L-07
The formal experiment evaluates sorting on oracle-certified valid Jordan
sequences. It does not evaluate recognition of arbitrary candidates or
invalid-input classification. Recognition remains a separate experimental
question, and no formal-experiment result is used as recognition evidence.

Within this scope, the experiment asks three empirical questions:
\begin{enumerate}
  \item Do all three implementations return the expected sorted output on the
        pre-specified valid cases?
  \item How do their measured-call runtime distributions vary across the
        tested sizes and controlled input families?
  \item What descriptive relationships appear between structural
        measurements, checked paper-operation counters, and runtime?
\end{enumerate}
The design answers these questions for one fixed collection of cases and one
recorded execution environment. Five input sizes are not used to infer
asymptotic complexity, and exploratory relationships are not interpreted as
causal effects.

\section{Pre-Specified Formal Protocol}
\label{sec:method-protocol}

% Claims: M-02, M-03; limitation L-08
The formal protocol was fixed before execution, and its complete configuration
was written before case generation or timing. The experiment uses the five
input sizes
\begin{equation}
  n \in \{32,64,128,256,512\}.
\end{equation}

At each size, the generator produces one \nolinkurl{flat_valid} case, one
\nolinkurl{nested_valid} case, and ten seeded \nolinkurl{incremental_valid}
cases. This gives twelve exact cases per size and sixty cases overall. The base
generation seed is \texttt{20261201}; each incremental case receives a
deterministic size- and case-specific seed. The flat and nested constructions
are deterministic.

The family balance is intentionally unequal. A size-level summary contains ten
incremental cases but only one flat and one nested case, so it mainly reflects
the incremental construction. Family-specific summaries preserve that
distinction. These controlled generators do not represent a probability sample
from all valid Jordan sequences.

\section{Compared Implementations}
\label{sec:method-implementations}

% Claims: M-04, M-06, M-07; limitation L-03
The pre-specified algorithm set contains three implementations.

\subsection{Python Sort}
\label{sec:method-python-sort}

The \nolinkurl{python_sort} baseline is the ordinary optimized sorting
implementation. Its timed call returns a sorted list and does not report
Jordan validity or structure.

\subsection{Simplified Reference Pipeline}
\label{sec:method-reference-pipeline}

The \nolinkurl{simplified_jordan_reference} entry times the complete
\texttt{simplified\_jordan\_sort} function. That call includes oracle
validation, operation-state preparation, family-tree construction for valid
inputs, structural statistics, reference trace construction, and serializable
result assembly. The timed result is therefore a complete oracle-backed
reference pipeline rather than only a sorting primitive.

\subsection{Paper Ordinary-List Implementation}
\label{sec:method-paper-implementation}

The fixed protocol registry names this entry
\nolinkurl{simplified_jordan_paper_ordinary_list}.

Its timed call invokes \texttt{paper\_jordan\_sort\_valid} with execution mode
\texttt{minimal} after the exact case has already passed oracle certification
and a separate checked diagnostic. As described in
\cref{sec:implementation-policies},
\texttt{minimal} disables trace recording, selected operation counters, and
complete backend commit validation while retaining the ordinary-list
Step~1/2/3 work, local safety checks, stage results, rollback, and final output
recovery.

These timed scopes are deliberately different. In particular, the reference
call includes certification and structural/reference work, whereas the paper
call uses a pre-certified input and times only its minimal sorting core. A
paper/reference ratio is therefore a pipeline-scope comparison, not a
like-for-like end-to-end speedup.

\section{Case Construction and Pre-Timing Audit}
\label{sec:method-case-audit}

% Claims: M-01, M-03, M-06, M-11
For each family, size, and case number, the runner generates the sequence once,
checks its length, and computes a SHA-256 digest of the serialized sequence.
Duplicate sequence hashes within a family-size group are rejected. The exact
sequence object is retained for all algorithms so that comparisons use matched
inputs.

Every sequence is passed to the oracle before any warm-up or measured call.
The runner requires a valid result with distinct values. It then computes the
structural profile, including interval counts, roots, nesting, depth, density,
and category fields. Failure at generation, certification, or profiling stops
the formal experiment rather than silently dropping the case.

The paper implementation also receives one untimed checked-state audit per
exact case through the checked diagnostic. The diagnostic output must match
\texttt{oracle\_result["sorted"]}, process all $n$ points, and report valid
state invariants. Its trace length and complete paper-operation metrics are
saved in \nolinkurl{case_audit.csv}. All sixty cases finish certification and
their checked-state audit before the first warm-up begins. This audit compares
independently constructed outputs; it does not make the paper core consume
oracle-sorted output, whose boundary is described in
\cref{sec:implementation-certification}.

\section{Timing Procedure}
\label{sec:method-timing}

% Claims: M-05, M-06, M-07, M-11, M-12
Each exact case-algorithm cell receives five warm-up calls followed by twenty
measured calls. The twenty calls estimate the timing distribution for one
fixed case and algorithm; they are not treated as twenty independent generated
inputs. Repeated calls and retained dispersion expose within-cell timing
variation; they do not convert repeated measurements of one input into
independent input samples
\parencites{mcgeoch2012guide}{kalibera2013benchmarking}.

For every warm-up and measured call, the runner creates a fresh Python list
from the stored sequence before starting the clock. It records elapsed time
with \texttt{time.perf\_counter\_ns()} around only the selected algorithm call.
If garbage collection is enabled before the call, the runner disables it for
the timed region and restores the caller's original GC state afterward. Each
algorithm's own output construction or recovery remains inside that call:
Python sort constructs its list, the reference pipeline constructs its result
dictionary, and the paper core executes
\texttt{state.partial\_order.to\_list()} before returning.

After the timer stops, the runner normalizes the already constructed return
value, for example by reading \texttt{result["sorted"]} from the reference
result. It then compares the normalized list with the oracle-sorted reference
and records correctness or error fields. These runner-level operations are
outside timing; they do not move any algorithm's own output construction
outside its timed call.

Warm-up failures abort the experiment. A measured-call exception is retained
as an error row with no valid timing rather than omitted. The formal evidence
contract and validator require every archived measured row to have a positive
time, valid oracle certification, correct output, a passed case audit, and no
error.

\section{Scheduling and Noise Controls}
\label{sec:method-scheduling}

% Claims: M-08, M-09
Case execution order is a deterministic shuffle under seed \texttt{20261203}.
Algorithm order is derived from seed \texttt{20261202} and the case index. Within
the twenty measured rounds, the initially shuffled three-algorithm order is
rotated cyclically, distributing algorithms across first, second, and third
positions. The warm-up order is generated by the same deterministic rule.

This schedule improves reproducibility and limits a fixed position bias, but it
does not remove all operating-system, thermal, frequency, or background-load
noise. This precaution is especially relevant because setup and ordering
choices can themselves introduce measurement bias
\parencite{mytkowicz2009wrong}. Variability remains visible in the raw calls
and case summaries.

\section{Aggregation and Statistical Units}
\label{sec:method-aggregation}

% Claims: M-05, M-09, M-10, M-11; limitations L-02, L-07
The raw evidence contains one row per exact case, algorithm, and measured
round:
\begin{equation}
  60\ \text{cases} \times 3\ \text{algorithms} \times
  20\ \text{measured calls} = 3600\ \text{raw rows}.
\end{equation}

The first aggregation level is the exact case-algorithm cell, giving 180 case
summaries. Its primary statistic is the median of the twenty measured calls.
Q1, Q3, IQR, mean, and sample standard deviation are retained to expose
dispersion. Q1 and Q3 use the median-of-halves convention: after sorting the
measured times, Q1 is the median of the lower half, Q3 is the median of the
upper half, and
\begin{equation}
  \operatorname{IQR}=Q3-Q1.
\end{equation}

The second stored level groups case medians by family, size, and algorithm,
giving 45 group summaries. Higher-level size and family tables used in the
analysis are also constructed from exact-case medians, not by pooling all raw
calls. This keeps the exact generated case as the unit of comparison.

Runtime ratios are first calculated within each exact case from its algorithm
medians. The case ratios are then aggregated with equal weight by size, family,
or family-size. This avoids dividing two independently pooled runtime
distributions and preserves the matched-case design.

Structural and checked-counter correlations are descriptive analyses over
matched case records. They are reported with explicit sample composition and
are not used as causal estimates, formal cost decompositions, or complexity
proofs.

\section{Evidence-Contract Validation}
\label{sec:method-validation}

% Claims: M-11, M-12
The separate fail-closed evidence-contract validator does not trust row-to-row
consistency alone. It reads the pre-specified and fixed protocol, independently
regenerates all sixty cases, recomputes case seeds
and sequence hashes, reruns oracle certification and structural profiling, and
executes checked paper diagnostics again. It compares the reconstructed
diagnostic output, processed count, trace count, and every paper metric with
\nolinkurl{case_audit.csv}.

The validator also verifies the complete case/round/algorithm product,
deterministic case and algorithm positions, positive timing values, correctness
fields, schema, row counts, and the absence of recorded errors. Case and group
summaries are recomputed from \nolinkurl{raw.csv}. Environment readiness, source
provenance, wall-clock consistency, manifest paths, and file hashes are checked
before a run is accepted. Malformed or inconsistent evidence produces
\texttt{valid=false} rather than authorizing analysis.

The archived validation report is retained with the run, and the analysis
performs a new validation pass before reading the evidence. This establishes
validation under the study's explicit evidence contract; it is not a
proof-theoretic formal verification of the algorithm.

\section{Execution Environment and Provenance}
\label{sec:method-environment}

% Claim: M-13; limitation L-06
The accepted formal experiment, bound to its exact execution and source version
in \cref{sec:method-evidence}, was recorded on Apple M4/arm64 with
\SI{16}{\giga\byte} memory, ten logical CPUs, macOS~26.6, and CPython~3.12.4.

Before timing, the runner recorded a clean Git worktree whose HEAD matched
remote \texttt{main}, AC power, a full battery, low-power mode disabled, low and
stable load, sufficient disk space, and no readiness warnings. These fields
describe the performance environment class rather than a personally
identifiable device.

Absolute runtimes in \cref{chap:results} apply to this one recorded execution.
They must not be generalized to other processors, operating systems, Python
versions, or machine states. Absolute times from the pilot and formal
experiments are not pooled; their comparison is restricted to within-run ratios
and directional patterns.

\section{Method Boundaries}
\label{sec:method-boundaries}

% Limitations: L-02, L-03, L-05, L-06, L-07, L-08
The method fixes the following interpretation limits:
\begin{itemize}
  \item recognition is separate from valid-input sorting;
  \item five tested sizes support observed-trend descriptions, not asymptotic
        inference;
  \item family imbalance must remain visible in aggregate interpretation;
  \item paper/reference ratios compare different pipeline scopes;
  \item repeated timing calls are not independent generated cases;
  \item one execution environment does not establish hardware-independent
        absolute time;
  \item cross-experiment comparison must not pool absolute runtimes; and
  \item structural and counter relationships remain exploratory and
        non-causal.
\end{itemize}
