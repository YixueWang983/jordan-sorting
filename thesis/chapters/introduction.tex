\section{Motivation and Scope}
\label{sec:introduction-motivation}
\label{sec:introduction-scope}

Sorting is one of the most basic problems in computing. For general inputs,
comparison-based sorting of $n$ elements requires $\Omega(n\log n)$
comparisons in the worst case; merge sort attains this bound, and randomized quicksort
attains it in expectation \parencite{cormen2009introduction}. When the input
has additional structure, sorting can be faster. Integer keys from a small
range, for example, can be sorted in linear time by counting or radix sort
\parencite{cormen2009introduction}.

Jordan sorting is such a special case. Its input lists the intersection
points of a simple curve with a line in the order in which the curve meets
them, and the task is to return their order along the line
(\cref{fig:jordan-sorting-problem}). Because a simple curve cannot cross
itself, not every order of the points can occur.
\Textcite{hoffmann1986sorting} showed that this restriction suffices for
sorting in linear time, and \textcite{fung1990simplified} later gave a
simpler linear-time procedure.

The problem arises in geometric algorithms that follow a polygon boundary but
need the resulting points in another order. In clipping a simple polygon
against a rectangular window, the intersections encountered along the polygon
boundary must also be ordered along the window's edges; Fung et~al.\ use
Jordan sorting as a step in their polygon-clipping algorithm
\parencite{fung1990simplified}. An error-correcting form of the task appears
in polygon triangulation \parencite{tarjan1988triangulating}, and a
generalized form is used to triangulate collections of disjoint polygonal
chains \parencite{baryehuda1994triangulating}.

These linear-time algorithms are considerably more complicated than merge sort
or quicksort. Their bounds rest on specialized dynamic lists: the 1986
algorithm uses level-linked search trees, and the 1990 paper proposes
heterogeneous finger trees that support insertion at either end in constant
amortized time and splitting in amortized time logarithmic in the size of the
smaller part. Such structures are intricate, and their asymptotic advantage
need not appear at practical input sizes; \textcite{sojka1997simple}
accordingly proposed simpler algorithms with weaker worst-case bounds,
intended to be practical at moderate input sizes.

This thesis implements the 1990 procedure and examines whether its
specialized structure pays off in practice. The procedure is implemented as one
Python core with two interchangeable backends for the sibling lists: ordinary
Python lists, which keep the control flow but lose the linear bound, and a
heterogeneous red--black finger tree, which supports it. The main experiment compares these backends directly.
A supplementary experiment compares both with merge sort and quicksort
implemented in Python, using CPython's built-in sort as a practical reference. The study combines algorithm reconstruction,
cost analysis and measurement in the sense of algorithm engineering
\parencites{sanders2009engineering}{mcgeoch2012guide}.

With either backend, the core maintains its own sorted output, pair forests
and sibling ownership. Inputs are pre-certified valid Jordan sequences with
distinct comparable values. Recognition, invalid-input behavior and geometric applications lie outside the study.

\section{Research Questions}
\label{sec:introduction-questions}

\begin{enumerate}[label=\textbf{RQ\arabic*:},leftmargin=*]
\item \textbf{Reconstruction and correctness:} Can the 1990 procedure be
implemented so that it computes the sorted order from its own maintained
state, using either ordinary lists or a finger tree, while preserving the
invariants of the pair hierarchy?
\item \textbf{Observed runtime:} On the same validated inputs, how do the
running times of the two backends compare with each other and with Python
implementations of merge sort and quicksort?
\item \textbf{Structure and cost:} Which properties of the implemented
operations yield the linear total-work bound, and how do the concrete
operation costs relate to the measured runtime?
\end{enumerate}

The correctness question is addressed through source-linked reasoning and
bounded execution checks. The runtime comparison uses paired measurement and
independent archive validation. The final question brings these analyses
together to relate the implemented operations to the measured runtime.

\section{Contributions and Findings}
\label{sec:introduction-contributions}
\label{sec:introduction-findings}

The reconstruction specifies the choices of orientation, geometric endpoint
and first point. Its tree provides stable identities, endpoint insertion,
local split/join and bounded header ownership updates. A manual argument links
reversed-pointer representation, locality and two potentials to linear total
source-level work. This bound assumes unit-cost comparisons and machine-word
operations, expected dictionary lookup and amortized growth.

The experiment compares ordinary lists with the uninstrumented tree on
\UnifiedN{} unique inputs from five sources: common, targeted, structural,
geometric and seeded. All inputs passed qualification, and the complete
formal attempt produced correct outputs throughout. The tree is faster on
\UnifiedWins{} inputs. The median tree/list ratio is \UnifiedMedian{}, with
range \UnifiedMinimum{}--\UnifiedMaximum{}.

Ratios decrease across the measured size bands. Within common, more heavily nested categories favor the tree more
often. The heavy inputs have at most one split and no two-sided split, whereas
the other sources extend coverage to interior and repeated splitting.
In the supplementary experiment, both general-purpose Python algorithms
finished sooner than either Jordan backend on every input.
