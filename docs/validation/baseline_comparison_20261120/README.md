# Jordan sorting 与通用排序的补充实验

2026 年 11 月 20 日。应导师在 11 月 19 日会议上的建议，本实验在已登记的 302 个有效 Jordan 输入上比较五种排序实现，输入长度为 32 至 513。**在每个输入上，纯 Python 的归并排序和快速排序都快于两个 Jordan 后端。** 以逐输入耗时比的中位数衡量，普通列表后端耗时为归并排序的 51.9 倍、快速排序的 88.7 倍；指树后端分别为 63.2 倍和 110.1 倍。四组配对比较中，最小差距为 36.7 倍。以下时间均来自这次五方法会话。主实验仍使用原有的双后端测量与报告。[登记协议](../../plan/baseline_comparison_protocol_20261120.md)

## 每个元素的键比较次数

**指树曲线较平缓，普通列表曲线波动较大。** 在 11 个精确长度上，指树的每元素比较次数中位数介于 **19.97 和 25.26** 之间。在 n = 512 和 513 时分别为 25.02 和 24.36；普通列表分别为 **70.48 和 28.12**。这两个长度的来源构成不同：512 组含 20 个几何输入，513 组没有几何输入。因此相邻点的落差同时包含输入构成的变化。归并和快排在 n = 512 上分别为 5.32 和 14.96 次。[图 2 · 五种方法每个元素的键比较次数](comparisons.pdf)

计数在单独的包装值运行中完成，每个输入、每种方法运行一次，累计输入键的四种序关系。相等性、哈希和对象身份检查不计入。Jordan 实现每处理一个点还需维护配对森林、兄弟列表和归属关系，这些工作可能带来运行时间开销。本实验只测了完整排序调用和键比较次数，无法给这些维护操作分摊耗时。对实际性能的结论限于本机、这些实现及所测输入规模；图中的走势也不足以确定渐近复杂度。

## 测量与复核

- 正式会话于柏林时间 **16:02:54 至 16:11:36** 完成，历时 **8 分 41 秒**。设备为 Apple M4、16 GiB 内存，系统为 macOS 27.2.1。启动命令使用的 Python 路径为 `/Users/schnee/.local/bin/python3`，版本为 CPython 3.12.14，与本次校准相同。两阶段记录的运行环境身份一致。正式会话前退出 Chrome、Claude 和“信息”，等待高负载后台任务回落；会话期间暂停用户 iCloud Drive 的 bird 进程，结束后恢复。
- 生产源码冻结在 `bca4c1c6`，协议提交为 `03e87e1cb`，测量及初次分析程序为 `0a0dcbd8a`。两个 Jordan 后端使用 minimal 模式；归并和快排直接调用冻结的 Python 实现。快排选当前子序列的中间元素作主元，按小于、等于、大于三路划分。五种方法使用同一批整数序列，正确性检查均在计时外。[输入清单](../input_suite_registry_20261101/suite.json)
- 准备档案含 **1,510 项输出检查、1,510 份键比较计数、34,920 个校准批次**。复核按每个输入与方法重算各候选 B 的三批中位时长，取首个达到 10 ms 的 B。正式会话含 **7,550 次预热、30,200 个正式批次**。所有正式批次共调用排序 **73,898,840 次**，运行器逐次检查了输出。正式会话的 **604 次**输入前后电源检查全部为 AC Power 且 lowpowermode = 0。
- 复核从两个原始日志和清单出发，检查了文件摘要、输出凭据、各输入的 B、种子排列、轮换及每个方法在每个顺位出现四次。每个正式批次以两次单调时钟读数之差除以 B，每个输入取二十批中位数。第二份独立脚本逐项核对了规模分档表中的比值与胜数，并给出报告引用的精确长度汇总和配对倍数。未筛选输入、删除异常批次或作显著性检验。[独立复核脚本](verify_results.py) · [复核结果](verification.json) · [准备与正式原始记录](raw_records.tar.gz)
