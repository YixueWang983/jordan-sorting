\section{Overall Comparison}
\label{sec:results-overall}
\label{sec:results-current}

The uninstrumented tree is faster on \UnifiedWins{} of the \UnifiedN{} measured
inputs; the ordinary list is faster on the remaining \UnifiedListWins{}.
There are no exact ties. Each input contributes one ratio $r_i$ of the tree's
median time to the list's median time, as defined in
\cref{sec:method-aggregation}.

Giving every input equal weight, the median ratio is \UnifiedMedian{}, with
range \UnifiedMinimum{}--\UnifiedMaximum{}.
\Cref{fig:results-distribution} shows the spread across inputs. A further descriptive count places \UnifiedNear{} inputs within
$0.98<r_i<1.02$. These inputs are approximately tied under this chosen band,
which was added after sampling. It leaves the strict $r_i<1$ count above
unchanged.

\section{Variation with Structure}
\label{sec:results-structure}

Structure is the clearest distinction within the common source.
\Cref{tab:results-nesting} compares its four predetermined categories.
Each category has the same representation across lengths, although the
strict-flat quota is smaller. The category medians decline from strict-flat

tree-faster inputs occur in the medium and heavy categories.

The heavy category contains the strongest tree advantages. Among its
\UnifiedHeavyN{} inputs, \UnifiedHeavyWins{} favor the tree. Every heavy input
has $S_i\leq1$, and none has a two-sided split; \UnifiedHeavyZero{} have no
split at all. Thus the advantage on these constructions does not require
frequent splitting. For the inputs without splits, it arises within the
remaining work of complete sorting.
One part of that remaining work grows with nesting depth in the ordinary
backend. Before each list creation, boundary insertion and transfer, its
liveness check walks the owner's parent chain to the family dummy and scans
the containing list at every ancestor (\cref{sec:implementation-complexity}).
The tree performs no such walk. The complete-sort timings do not measure
how much of the ratio this difference accounts for.

\subsection{Nesting Categories by Length}
\label{sec:results-nesting-by-length}

The category medians in \cref{tab:results-nesting} pool all ten measured
lengths. We also computed the median of the per-input ratios $r_i$ for
each category at each exact length in the common source. At all ten
lengths, the median is highest for strict-flat inputs, followed by low,
medium and heavy nesting. \Cref{fig:results-nesting-by-length} shows the

stay above 1 at every measured length.

\section{Comparison with General-Purpose Sorting}
\label{sec:results-baselines}

On every one of the \BaselineInputs{} inputs, both Python baselines finished
sooner than either Jordan backend. The median paired time ratios for the
ordinary list were \BaselineListMerge{} against merge sort and
\BaselineListQuick{} against quicksort. For the finger tree, the corresponding
ratios were \BaselineTreeMerge{} and \BaselineTreeQuick{}. Each ratio uses
the two times for the same input in the supplementary session.

\paragraph{Growth across size bands.}
The common and geometric sources contribute \BaselineCommon{} and
\BaselineGeometric{} inputs, respectively, to each band. Pooling them holds
those source counts fixed. For each method we took the median across the
\BaselinePerBand{} input-level medians in each band and divided by its
first-band value (\cref{fig:baseline-growth}). Across the four adjacent
transitions, the tree's empirical exponent ranged from \BaselineTreeMin{}
to \BaselineTreeMax{}, the closest to one among the four Python
implementations at each transition. The ordinary list grew most steeply
in the last transition, with exponent \BaselineListLast{}.

\begin{figure}[htbp]
\centering
\includegraphics[width=\linewidth]{baseline_growth.pdf}
\caption[Relative growth across size bands]{Post hoc analysis of archived timings; no additional measurements were taken. Common and geometric have the same source counts in every band (\BaselineSubset{} inputs in total). Nominal lengths are the lower band endpoints. Panel (a) normalizes each method and each reference curve to the first band. Panel (b) shows $\log_2(T_{j+1}/T_j)$ for adjacent band medians; the horizontal lines mark linear and quadratic reference growth.}
\label{fig:baseline-growth}
\end{figure}

Across the five size bands in \cref{fig:baseline-growth}, median sorting time
grew by a factor of \BaselineTreeGrowth{} for the Jordan finger tree,
\BaselineMergeGrowth{} for Python merge sort, and \BaselineQuickGrowth{} for
Python quicksort. The finger tree thus showed slower growth than either Python
baseline over the measured range, while CPython's built-in \texttt{sorted()}
showed the slowest growth of all five methods (\BaselineBuiltinGrowth{}-fold).
Using all inputs gave similar first-to-last factors for the tree
(\BaselineTreeAllGrowth{} vs.\ \BaselineTreeGrowth{} in the fixed-source
subset) and list (\BaselineListAllGrowth{} vs.\ \BaselineListGrowth{}).
The largest change across methods was \BaselineMaxSensitivity{}\%.
In the full set, source composition varies between bands.

\paragraph{Key comparisons.}
The ordinary list used more order comparisons per element than either
Python baseline on every input. The tree used more than merge sort on
every input and more than quicksort on \BaselineTreeMoreQuick{} inputs.
On the remaining \BaselineTreeFewerQuick{}, it used fewer comparisons than
quicksort and still took longer. Thus the key comparison count alone cannot
account for the observed ordering of running times.

\section{Summary of Observations}
The tree is faster on \UnifiedWins{} of \UnifiedN{} inputs, with a median
tree/list ratio of \UnifiedMedian{}. Median ratios fall across the measured
size bands, and each of the four sources measured over several size bands
(common, structural, geometric, seeded) has a lower median at its largest
length than at its smallest. The tree's largest advantages occur on heavily
nested inputs with almost no splitting. Neither the selected split parameter
$k$ at a fixed length nor the two-sided split fraction shows a clear
relationship with the complete-sort ratio.
In the separate supplementary comparison, both Python general-purpose sorts
were faster than either Jordan backend throughout the measured set.
