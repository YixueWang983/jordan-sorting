第 1 页
Simplified Jordan Sorting 的可执行重构进展

大家好。这次汇报介绍我的硕士论文进展，主题是使用普通 Python list 对 Simplified Jordan Sorting 进行可执行重构。输入按沿曲线遇到交点的顺序给出；任务是恢复这些点沿横坐标轴的顺序。上次汇报聚焦静态结构，包括 rank interval、upper 和 lower pair family、family tree，以及 oracle 支持的 reference。核心问题是，论文中的动态过程能否维护自身状态，并从中恢复输出。我将重点解释两处重构决定，再介绍验证检查和正式实验的运行时间结果。

============================================================

第 2 页
上一次汇报建立了静态结构基线

上次实现用 rank interval 表示输入，区分 upper 和 lower pair family，重构 laminar family tree，并计算结构指标。Oracle 检查输入有效性并提供参考答案。尚未实现的是动态过程：更新 processed prefix、拆分 sibling list、转移 ownership，以及从维护状态恢复输出。每次更新都必须保持 partial order 和 family structure 一致。一次更新出错就可能同时破坏两者，因此安全的动态更新是当时的主要实现缺口。

第 3 页
上次汇报后的进展

此后，我将范围缩小到外部 oracle 已认证的有效输入，并实现 Step 1、Step 2 和 Step 3 控制流。我加入 ownership 检查、事务式更新、重放和有界验证。实现通过这些检查后，我按固定协议运行了正式实验。当前成果是可执行的普通列表重构。

第 4 页
当前范围：有效输入排序

论文研究的是 1990 年 sorting procedure 在 oracle 已认证有效的输入上的运行。实验比较 Python sort、完整的 oracle-backed reference pipeline 和重构后的 paper core。Recognition 不在本次实验范围内。当前 core 使用普通 Python list，尚未实现历史线性时间分析所使用的专用后端。

第 5 页
三个问题连接重构、测量与解释

RQ1 是主要技术问题：普通列表重构能否在认证后的有效输入上，从维护状态恢复正确排序？RQ2 比较 paper call、Python sort 和完整 reference pipeline 在各自计时范围下的表现。RQ3 探索输入结构、checked operation counter 与运行时间之间的描述性关系，不作因果解释。 本次汇报重点介绍 RQ1，以及 RQ2 中的运行时间基线；不展开结构与成本关系的分析。

============================================================

第 6 页
Oracle、reference pipeline 与 paper core 承担不同角色

Paper call 之前，oracle 认证输入有效性；调用之后，runner 将返回值与 oracle 的排序结果比较。Reference pipeline 使用完整 oracle result，包括 sorted output。Paper core 只接收原始序列，并以已认证有效为前提。它执行 Step 1、Step 2 和 Step 3，维护 partial order 与 sibling list，再从 partial order 恢复输出。两条路径使用同一个 expected answer 检查，但输出来源不同。Oracle 的排序答案不会进入 paper core，因此图中的虚线比较框位于 core 外部。

============================================================

第 7 页
初始化一次，再逐点更新

我们同时维护两种信息：已处理点的排序，以及 pairs 之间的父子关系。初始化只做一次，仅将前三个点按 x 坐标排序，这个有序列表称为 S₃。同时建立 upper、lower pair family，不使用 oracle 的排序答案。点的编号和 pair 的端点存储仍保持曲线顺序。从第 4 个点开始，每轮加入一个新点。我们从沿曲线的前一个点出发。Step 1、2 利用它在有序列表中的邻居，分别找到 predecessor boundary Aᵢ 和 successor boundary Bᵢ。Step 3(a) 将新 pair 放入 family 结构，并确定它的 parent。Step 3(b) 在需要时拆分 sibling list，让新包含的旧 pairs 成为新 pair 的 children。到这时，Step 3(c) 才根据维护的状态选择 anchor，将新点插入有序列表。Increasing 时，Step 3(a) 使用 Aᵢ，3(b) 使用 Bᵢ。Decreasing 交换两者的用途，并镜像左右操作；Step 1、2 仍分别返回 Aᵢ、Bᵢ。论文描述 increasing 情形；decreasing 来自对称重构，anchor 的细节属于可执行化澄清。这些类别说明重构的依据，并不分别对应某个步骤。

============================================================

第 8 页
从 S₃ 到 S₄：插入需要几何 anchor

输入是 (3,2,1,4)。初始化后，有序列表是 [1,2,3]，但点的编号仍然按照曲线访问顺序保留。

现在插入第四个点，也就是 4。Step 3(b) 完成后，新 upper pair P₄ 的端点是 (1,4)，它有一个 child：P₂，按曲线顺序存为 (3,2)。

本次从 1 到 4，因此是 increasing。Child 的几何区间 [2,3] 位于新 pair 的区间 [1,4] 内。因此，4 必须排在 child 的两个端点之后。Child 的右边界是 3，所以我们选择 3 作为 anchor。

如果把 4 紧挨着插在 2 后面，它就会落在列表中 child 的两个端点之间，得到 [1,2,4,3]。插在 3 后面，才得到 [1,2,3,4]。

我们也可以把端点按从左到右的顺序存储，前提是保留它们的曲线身份信息。真正的错误，是把“曲线顺序中的第二个端点”当成“几何右端点”。

我将这一明确选择记录为可执行化澄清，而不是 1990 年论文的逐字规则。

第 9 页
为什么需要单独检查 z₁ 输出锚点

这里在第 7 次迭代插入 0。结束下标为奇数，因此新 pair 属于 lower family；0 小于旧端点 7，因此本次为 decreasing。Step 3(b) 后，新 pair 获得图中的 P₃ 和 P₅。Step 3(c) 取最左 child P₃ 的几何左端点。P₃ 的端点为 2 和 3，所以 base anchor 是 2。但是 z₁ 的值为 1，它不是任何 lower pair 的端点，却仍在有序列表中。若直接把 0 插在 2 前，会让 0 留在 1 后面。本例下标为奇数，且 0 小于 z₁，z₁ 又小于 base anchor，因此最终 anchor 改为 z₁。这只改变输出插入，不替代先前的 boundary-pair selection。

第 10 页
Ownership 安全的拆分与转移

这里的 ownership 指一张 children list 归哪个 parent pair 管理。当 children 转移时，parent 记录和列表归属必须一起保持一致。拆分前，原 parent 拥有两个片段。拆分后，它保留 retained segment，新 parent 接收 acquired segment。两个非空侧都可能得到新 list，但只有 acquired segment 改变 parent。Split 和 transfer 构成一个 transaction：保存受影响状态，执行更新，再检查边界和 ownership。若检查失败，rollback 恢复之前的状态。普通列表会产生扫描、复制、切片和 ownership rebinding 成本。这些检查不能建立历史线性时间分析所需的更新界。

第 11 页
实现检查与实验一致性

左侧检查实现及其内部状态；右侧检查保存的实验记录，并重新计算汇总。左侧是互补的检查方式，包括重点回归用例、n 不超过 8 的全部 2,074 个 oracle-valid permutation，以及对 parent link、ownership、sibling list 和恢复输出的 checked-state audit。确定性重放比较同一 core 多次运行后的状态，并不是第二套独立实现。右侧将归档记录与固定实验设置及重算汇总核对。这些有限证据不是对所有 Jordan sequence 的数学证明。

第 12 页
运行时间实验：输入与测量

实验测试从 32 到 512 个点的 5 个规模。每个规模有 1 个 flat、1 个 nested 和 10 个逐步生成的有效输入，共 60 个。Flat 输入递增；nested 输入交替取剩余值中的最小值和最大值。Incremental 生成使用固定种子并检查有效性。每种算法对每个输入预热 5 次、测量 20 次，共 3,600 条记录。重复调用使用 fresh list，算法位置轮转。认证及每个 case 一次的 checked-state audit 位于 paper 计时前。Minimal 模式对全部点运行相同核心，省略详细 trace 和部分诊断检查。Paper 计时包含初始化、Step 1 至 3 和输出恢复。输出比较在计时后。Python 计时覆盖排序；reference 计时覆盖完整 oracle-backed pipeline。运行时间页展示 paper 和 Python。

============================================================

第 13 页
运行时间实验中的 60 个用例均返回正确输出

本次运行时间实验中的 60 个 case 均通过认证，并各通过一次 checked-state audit。每次 measured call 都返回 expected output，没有记录正确性错误。3,600 条测量记录携带各自的 case-level audit 结果，不代表进行了 3,600 次独立 audit。这些结果仅覆盖本次测试的有效用例。

第 14 页
普通列表实现的运行时间基线

这一页展示普通列表 paper core 的运行时间，并以 Python sort 作为实际排序基线。

两种方法接收相同的有效输入，各自产生排序结果。认证和外部检查位于计时之外。每种方法自身的输出构造仍在计时内。

图中每个数值是同一规模下 12 个 case 中位数的中位数，每个 case 权重相同。每个 case 的中位数来自 20 次计时调用。纵轴采用对数刻度。

Paper 的耗时从 32 个点时约 0.59 毫秒，上升到 512 个点时约 18.72 毫秒。Python sort 在每个测试规模上的中位耗时都低得多。

这些结果描述当前实现，不能证明线性时间性能，也没有隔离各个组成部分的成本。它们为后续优化和后端比较提供基线。

第 15 页
当前证据说明了什么

当前证据支持一个从维护状态恢复输出的可执行普通列表重构，并在运行时间实验中的 60 个用例上得到正确结果。运行时间趋势描述的是当前实现及其计时范围。普通列表不构成线性时间实现，五个测试规模也不能确定渐近复杂度。本实验没有评估 recognition。

第 16 页
可能的下一步：finger-tree 后端

Finger-tree 后端是可能的未来扩展，不属于当前实验证据。它将保持相同的 Step 1、Step 2 和 Step 3 行为。普通列表实现为检查新后端的行为提供了经过测试的参照点。我希望向导师确认两个问题：应实现历史 heterogeneous finger tree，还是支持所需列表操作的等价后端？一个经过测试、语义等价的原型是否足够，还是还应证明所需的摊还操作界？
