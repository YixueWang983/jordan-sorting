\section{Motivation and Scope}
\label{sec:introduction-motivation}
\label{sec:introduction-scope}

Jordan sorting recovers coordinate order from the traversal order of a simple
curve's intersections with a line. The geometric restrictions permit
linear-time algorithms \parencites{hoffmann1986sorting}{fung1990simplified}
when their specialized dynamic-list operations meet the required cost bounds.
The problem arises in clipping a simple
polygon against a rectangular window: intersections encountered along the
polygon boundary must also be ordered along the window's edges. Fung et al.\
use Jordan sorting as a step in their polygon-clipping algorithm
\parencite{fung1990simplified}.

Replacing these structures with ordinary Python lists can preserve semantics
while changing complexity. A structure with a better asymptotic bound may
still run more slowly at practical input sizes. This thesis examines the
relationship between cost bounds and observed runtime by combining algorithm
reconstruction, cost analysis and measurement in an algorithm-engineering study
\parencites{sanders2009engineering}{mcgeoch2012guide}.

Since the September progress report, which presented the ordinary-list
implementation and its runtime baseline, the scope has expanded to include
a finger-tree backend, its amortized analysis and a direct comparison of the
two backends.

Both backends share one Python core for the 1990 procedure. With either
backend, the core maintains its own sorted output, pair forests and sibling
ownership. Inputs are pre-certified valid Jordan sequences with distinct
comparable values. Recognition, invalid-input behavior and geometric
applications lie outside the study.

\section{Research Questions}
\label{sec:introduction-questions}

\begin{enumerate}[label=\textbf{RQ\arabic*:},leftmargin=*]
\item \textbf{Reconstruction and correctness:} Can the 1990 procedure be
implemented so that it computes the sorted order from its own maintained
state, using either ordinary lists or a finger tree, while preserving the
invariants of the pair hierarchy?
\item \textbf{Observed runtime:} How do the two backends compare in running
time on a fixed set of validated inputs under a paired measurement protocol?
\item \textbf{Structure and cost:} Which properties of the implemented
operations yield the linear total-work bound, and how do the concrete
operation costs relate to the measured runtime?
\end{enumerate}

The correctness question is addressed through source-linked reasoning and
bounded execution checks. The runtime comparison uses paired measurement and
independent archive validation. The final question brings these analyses
together to relate the implemented operations to the measured runtime.

\section{Contributions and Findings}
\label{sec:introduction-contributions}
\label{sec:introduction-findings}

The reconstruction specifies the choices of orientation, geometric endpoint
and first point. Its tree provides stable identities, endpoint insertion,
local split/join and bounded header ownership updates. A manual argument links
reversed-pointer representation, locality and two potentials to linear total
source-level work. This bound assumes unit-cost comparisons and machine-word
operations, expected dictionary lookup and amortized growth.

The study compares the backends on 140 controlled inputs, a separate
twelve-input split set and a later eighteen-input structural extension.
All inputs passed validation on both backends, and all 69,360 formal sample
calls return correct output in 6,800 batches.
The measured tree retains instrumentation hooks, which intercept field
reads and writes, with work counting disabled. Its median runtime exceeds
the list's on every input. Across the common and targeted sets, the within-input
tree/list ratios have medians 2.898 and 3.180, and ranges 1.114--3.535 and
3.147--3.213, respectively.
The structural extension has a median ratio of 2.987 and range 2.376--3.222;
its later measurement session is analyzed separately.

The common workload has no two-sided splits. The targeted set exercises that
path with smaller-side sizes of 3/7/19. These workloads provide complementary
views of the implementations: the common set covers endpoint insertion and
whole-group transfer, while the targeted set also exercises interior splitting.
The structural extension adds larger balanced and skew splits and repeated
splits of earlier outputs.
