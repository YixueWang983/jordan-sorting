第 1 页
Simplified Jordan Sorting 的可执行重构进展

大家好。这次汇报介绍我的硕士论文进展，主题是使用普通 Python list 对 Simplified Jordan Sorting 进行可执行重构。上次汇报聚焦静态结构，包括 rank interval、upper 和 lower pair family、family tree，以及 oracle 支持的 reference。核心问题是，论文中的动态过程能否维护自身状态，并从中恢复输出。我将重点解释两处重构决定，再介绍验证检查和正式实验的运行时间结果。

============================================================

第 2 页
上一次汇报建立了静态结构基线

上次实现用 rank interval 表示输入，区分 upper 和 lower pair family，重构 laminar family tree，并计算结构指标。Oracle 检查输入有效性并提供参考答案。尚未实现的是动态过程：更新 processed prefix、拆分 sibling list、转移 ownership，以及从维护状态恢复输出。每次更新都必须保持 partial order 和 family structure 一致。一次更新出错就可能同时破坏两者，因此安全的动态更新是当时的主要实现缺口。

============================================================

第 3 页
上次汇报后的进展

此后，我将范围缩小到外部 oracle 已认证的有效输入，并实现 Step 1、Step 2 和 Step 3 控制流。我加入 ownership 检查、事务式更新、重放和有界验证。实现通过这些检查后，我按固定协议运行了正式实验。当前成果是可执行的普通列表重构。

============================================================

第 4 页
当前范围：有效输入排序

论文研究的是 1990 年 sorting procedure 在 oracle 已认证有效的输入上的运行。实验比较 Python sort、完整的 oracle-backed reference pipeline 和重构后的 paper core。Recognition 不在本次实验范围内。当前 core 使用普通 Python list，尚未实现历史线性时间分析所使用的专用后端。

============================================================

第 5 页
三个问题连接重构、测量与解释

RQ1 是主要技术问题：普通列表重构能否在认证后的有效输入上，从维护状态恢复正确排序？RQ2 比较 paper call、Python sort 和完整 reference pipeline 在各自计时范围下的表现。RQ3 探索输入结构、checked operation counter 与运行时间之间的描述性关系，不作因果解释。

============================================================

第 6 页
Oracle、reference pipeline 与 paper core 承担不同角色

Paper call 之前，oracle 认证输入有效性；调用之后，runner 将返回值与 oracle 的排序结果比较。Reference pipeline 使用完整 oracle result，包括 sorted output。Paper core 只接收原始序列，并以已认证有效为前提。它执行 Step 1、Step 2 和 Step 3，维护 partial order 与 sibling list，再从 partial order 恢复输出。两条路径使用同一个 expected answer 检查，但输出来源不同。Oracle 的排序答案不会进入 paper core，因此图中的虚线比较框位于 core 外部。

============================================================

第 7 页
Step 1/2/3 控制流与镜像方向

算法先排序 z1、z2、z3，再初始化 partial order 和首批 upper、lower pair。对每个新点，Step 1 找 predecessor boundary pair A_i，Step 2 找 successor boundary pair B_i。Step 3(a) 插入 pair，Step 3(b) 在需要时拆分 sibling list 并转移 ownership；这两步更新 pair family。Step 3(c) 将新点插入维护的顺序。在 increasing iteration 中，Step 3(a) 使用 A_i，Step 3(b) 使用 B_i；decreasing iteration 交换两者的用途。论文直接描述 increasing case，decreasing case 由对称性重构。两个方向共享相同阶段，但局部角色互为镜像。接下来两页解释两处可执行化澄清：几何端点与奇数索引 z1 输出 anchor。

============================================================

第 8 页
Step 3(c) 使用几何极值，而非第二个存储端点

考虑有效前缀 (3,2,1,4)。Acquired pair P2 按 curve order 存为 (3,2)。若取第二个存储元素 2 为 anchor，得到 (1,2,4,3)，在 axis order 上是错误的。Step 3(c) 需要几何极值，而不是 curve order 中的第二个元素。这里正确的 anchor 是 3，将 4 插在 3 后得到 (1,2,3,4)。Pair 记录沿曲线的遍历顺序，插入则必须遵循 axis order。这是表示方式的问题：curve order 未必能标识 axis order 中所需的一侧。Increasing iteration 使用右端几何极值，decreasing iteration 使用左端几何极值。这属于可执行化澄清，因为 1990 年论文没有以这种形式明确给出规则。缺少这一澄清时，有效输入的例子也会失败。

============================================================

第 9 页
为什么需要单独检查 z₁ 输出锚点

这里在第 7 次迭代插入 0。结束下标为奇数，因此新 pair 属于 lower family；0 小于旧端点 7，因此本次为 decreasing。Step 3(b) 后，新 pair 获得图中的 P₃ 和 P₅。Step 3(c) 取最左 child P₃ 的几何左端点。P₃ 的端点为 2 和 3，所以 base anchor 是 2。但是 z₁ 的值为 1，它不是任何 lower pair 的端点，却仍在有序列表中。若直接把 0 插在 2 前，会让 0 留在 1 后面。本例下标为奇数，且 0 小于 z₁，z₁ 又小于 base anchor，因此最终 anchor 改为 z₁。这只改变输出插入，不替代先前的 boundary-pair selection。

============================================================

第 10 页
Ownership 安全的拆分与转移

每个有限 pair 只有一个 parent 和一个 sibling-list owner。拆分前，原 owner 控制 retained 和 acquired 两部分。拆分后，原 owner 保留 retained segment，新 owner 接收 acquired segment。两个非空侧都可能得到新 list，但只有 acquired segment 改变 parent。Split 和 transfer 构成一个 transaction：保存受影响状态，执行更新，再检查 split boundary、ownership 和局部后置条件。若检查失败，rollback 恢复 registry、ownership link 和 list ID。维护状态还包括已处理前缀的排序结果，以及两类 pair family。普通列表会产生扫描、复制、切片和 ownership rebinding 成本。这些正确性检查不能建立历史线性时间分析所需的更新界。

============================================================

第 11 页
实现检查与实验一致性

Focused regression case 覆盖已知边界条件。有界穷举验证覆盖 n 不超过 8 的全部 2,074 个 oracle-valid permutation。Checked-state audit 检查 parent link、ownership、sibling list 与恢复输出。确定性重放比较同一 core 多次运行后的状态，并不是第二套独立实现。重放检查的是同一过程是否得到一致状态。另有实验检查，将保存的输出与固定设置及重算汇总比较，详情见 Backup C。这些有限证据支持已评估用例，但不是对所有 Jordan sequence 的数学证明。

============================================================

第 12 页
正式实验将认证与 audit 保持在 paper 计时之外

实验使用 5 个规模，每个规模 12 个 exact case，并比较 3 个算法。每个 case-algorithm cell 包含 5 次 warm-up 和 20 次 measured call，共得到 3,600 条测量记录。这 20 次调用重复同一个 exact case，并非 20 个独立输入。每次调用获得包含相同值的 fresh list。算法位置轮转，避免某个算法总是先运行。Paper 的认证与 checked-state audit 在计时前完成。Paper 计时包含 minimal core call，以及从维护顺序恢复输出。输出比较发生在计时后。Python 计时覆盖排序调用；reference 计时覆盖完整的 oracle-backed pipeline。这是三种不同的计时范围。

============================================================

第 13 页
全部 60 个评估用例均返回正确输出

全部 60 个 case 均通过认证，并各通过一次 checked-state audit。每次 measured call 都返回 expected output，没有记录正确性错误。3,600 条测量记录携带各自的 case-level audit 结果，不代表进行了 3,600 次独立 audit。这些结果仅覆盖本次测试的有效用例。

============================================================

第 14 页
Paper/reference 比值随五个测试规模下降

对每个 case，我用 paper 调用时间的中位数除以 reference 调用时间的中位数。然后对每个规模下的这些比值取中位数。比值在 n 为 32 时是 3.226，64 时是 2.202，128 时是 1.351，256 时是 0.851，512 时是 0.567。因此，128 时比值大于 1，256 时小于 1。在这些计时范围下，两个较大规模的 paper 调用耗时更少。由于计时范围不同，这不能证明端到端加速。Python sort 在每个测试规模上都有最低的调用时间中位数，见 Backup A。

============================================================

第 15 页
当前证据说明了什么

当前证据支持一个从维护状态恢复输出的可执行普通列表重构，并在已评估用例上得到正确结果。运行时间趋势描述的是当前实现及其计时范围。普通列表不构成线性时间实现，五个测试规模也不能确定渐近复杂度。本实验没有评估 recognition。

============================================================

第 16 页
可能的下一步：finger-tree 后端

Finger-tree 后端是可能的未来扩展，不属于当前实验证据。它将保持相同的 Step 1、Step 2 和 Step 3 行为。普通列表实现为检查新后端的行为提供了经过测试的参照点。Backup E 说明接口及 ownership-transfer 难点。我希望向导师确认两个问题：应实现历史 heterogeneous finger tree，还是支持所需列表操作的等价后端？一个经过测试、语义等价的原型是否足够，还是还应证明所需的摊还操作界？

第 20 页 | 问答备用
备用 D：镜像后的局部选择

这张表汇总镜像后的局部选择。Step 1 始终计算 predecessor-side boundary A_i，Step 2 始终计算 successor-side boundary B_i。镜像发生在 Step 3 如何使用这些 boundary。在 increasing iteration 中，获得左侧拆分片段，并使用最右 child 与右侧几何端点；decreasing iteration 则镜像为右侧拆分片段、最左 child 与左侧几何端点。

------------------------------------------------------------

第 21 页 | 问答备用
备用 E：拟议的 finger-tree 后端边界

拟议结构把 Step 1、Step 2 和 Step 3 放在一个小型 sibling-list 接口之上。普通列表后端仍是当前已验证的基线。拟议的 finger-tree 后端将独立实现相同的语义操作：创建 singleton list、在左或右边界插入、按新点值拆分、访问 first/last child，以及保持 ownership 和 stable handle。具体目标是历史 heterogeneous finger tree，还是具有等价操作界的后端，仍需与导师确认。主要风险是，高效 tree split 本身不够；若 ownership transfer 仍扫描 acquired segment 并逐项重新绑定，后端就可能无法满足历史分析所需的操作界。第一步应先保证语义等价与 differential correctness，任何复杂度主张都需要独立的证明论证。
